# AGENTS.md

omp-vcc is an extension for omp (oh-my-pi) and Pi: algorithmic compaction (no LLM call), pinned notes, and `vcc_recall` over the raw session history and the project's other sessions. A fork of pi-vcc. Each host has its own entry written against that host's own code, which is its API (`index.ts` for omp, `pi.ts` for Pi), over one shared core. User-facing docs are in `README.md`; keep it short and put contributor notes here.

## Checks

```sh
bun install --frozen-lockfile --ignore-scripts
bun run setup:omp
bun run setup:pi
bun run typecheck
bun run test
```

omp is not a dependency: it releases often, and a pinned copy would test a version users have long updated past. `bun run setup:omp` installs the latest omp into `node_modules` without saving it (`OMP_VERSION=18.14.0 bun run setup:omp` for another one); typecheck and the suite need it, since tests drive the hook with omp's own `convertToLlm` (`tests/support/host.ts`), read sessions with omp's own parser (`tests/support/load-session.ts`), and `tests/omp-host.test.ts` runs omp-vcc inside a real omp session. omp needs a recent Bun (its `engines.bun`). Pi is not a dependency either: `bun run setup:pi` installs the latest Pi (`@earendil-works/pi-coding-agent`; `PI_VERSION=1.0.0 bun run setup:pi` for another one), and `tests/pi-host.test.ts` runs omp-vcc inside a real Pi session built with Pi's own SDK, `tests/pi-entry.test.ts` drives `pi.ts` with a fake Pi API, and `tests/context-edits.test.ts` checks the context-edit projection against Pi's own `buildSessionContext`; each skips where Pi is not installed. Install omp first, then Pi (`setup:omp`, `setup:pi`); each entry's typecheck reads both hosts' types. `bun run test` is `bun test --isolate`, each file in a fresh module registry: once omp is loaded in a process it answers Pi's package names with its own (its shim for Pi extensions on omp), so a Pi test after an omp test in one registry would test omp's copy. `tests/support/pi.ts` makes every Pi test check it has the real Pi (`assertRealPi`) and fail with that explanation otherwise; npm may also nest Pi's `pi-ai` under Pi's package, so resolve Pi's own dependencies from Pi's directory. `tests/pi-shapes.test.ts` runs Pi's message roles and `edit` shape through the hook on Pi's `convertToLlm`. CI runs everything against the latest of both hosts and against the floor of each peer range in `package.json`, on every push and pull request and weekly.

`tests/long-horizon.test.ts` holds the long-horizon floor: 60- and 120-turn sessions with planted facts, worked through by a real model in omp, or in Pi with `OMP_VCC_LH_HOST=pi` (`tests/support/long-horizon.ts`; the session is opened by `tests/support/host-session.ts`, with the provider in omp's `models.yml` or Pi's `models.json`, and Pi's `/compact` standing in for omp's idle pass, which Pi does not have). Nothing stands in for omp or the model: the model is a real provider set up as a user sets one up (a `models.yml` provider whose key omp reads from the environment): DeepSeek V4.1 Flash (`deepseek/deepseek-v4.1-flash` on OpenScale, `https://api.openscale.so/v1`), run when `OMP_VCC_LH_API_KEY` in the environment holds a key for it (`OMP_VCC_LH_BASE_URL`, `OMP_VCC_LH_MODEL` and `OMP_VCC_LH_API` point it elsewhere); without it the tests are skipped, as they are in CI. The benchmark scripts also read it from `research/long-horizon.env` (git-ignored, `OMP_VCC_LH_API_KEY=…` lines); the tests do not, so a plain `bun test` never starts hours of model turns. Each turn is a request telling the agent what to do (read a module, make an edit, run its tests, commit); the agent does it through omp's real tools on a real project in a real git repository with real `bun test` tests (each turn's pass once its edit is made; turn 25's fails on rounding until the agent fixes it). omp counts the context from the provider's usage, compacts on its threshold and in its idle pass every 6 turns, and commits each compaction; omp-vcc is loaded from this package, and recall runs through the session's `vcc_recall` tool. The facts are found afterwards in the session by content and omp-vcc's `#N`. A run takes about an hour (300 model turns). omp builds child shells' env from the env it loaded with, so nothing the session runs may depend on a `PATH` set later. `bun run scripts/benchmark-long-horizon.ts` prints the per-fact table (`… 60 6 all` for a 32K, 128K and 1M window); run it before and after a change to the summary or recall.

`scripts/benchmark-cybench.ts` (`tests/support/cybench.ts`) runs [Cybench](https://arxiv.org/abs/2408.08926) (Apache-2.0) as one long session on the same model, in omp or, with `--host=pi`, in Pi (its logs then start `cybench-pi-`; both benchmark scripts take `--host`): its 17 file-only capture-the-flag tasks (binaries to reverse, a pcap, emails, crypto) back to back in omp, answering each task's own subtask questions, then the same questions asked again tasks later, with omp-vcc, omp-vcc without `[Working Set]`, or the host's own compaction (`vcc`, `vcc-no-ws`, `own`; `omp` is the old name for `own`). It fetches Cybench at a pinned commit into `research/cybench` and sets each task up with the task's own `init_script.sh`, and the agent then inspects and runs the challenge binaries: it runs code from outside this repository, so run it in a sandbox or a throwaway container, never on a machine that matters. `.claude/settings.json` allows that one command (`bun run scripts/benchmark-cybench.ts …`) so an agent session can run it without a prompt; keep the key in `research/long-horizon.env` so the command stays that plain. It is a benchmark, not a test: nothing in `bun test` runs it.

omp's own docs ship inside its package (`dist/docs-index.generated.txt`: a JSON list of names, a newline, then a base64 gzip of the bodies); `extensions.md`, `compaction.md` and `session.md` cover what omp-vcc uses. Its sources are in `node_modules/@oh-my-pi/pi-coding-agent/src` (`session/messages.ts` for `convertToLlm`, `extensibility/shared-events.ts` for the events). Pi's docs are in `node_modules/@earendil-works/pi-coding-agent/docs` (`extensions.md`, `compaction.md`, `session-format.md`, `sdk.md`), its types in `dist/core/extensions/types.d.ts` and `dist/core/session-manager.d.ts`, and its code in `dist/` (`core/agent-session.js` for the compaction flow, `core/compaction/compaction.js` for `shouldCompact`, `core/session-manager.js` for the context projection).

## The Lisp core

`lisp/` is omp-vcc's core in Common Lisp on SBCL, being ported from the TypeScript under `src/` one module at a time; so far recall's term search (`lisp/src/search.lisp`, from `src/core/search-entries.ts`) and its reading of session files (`lisp/src/session.lisp`: the entries, `#N`, the active branch, a fork's parents and the kept originals, from `session-file.ts`, `raw-store.ts` and `load-messages.ts`; `lisp/src/render.lisp`: each message as recall renders it and search reads it, from `content.ts`, `tools.ts` and `render-entries.ts`). recall-run.ts hands the core file paths and the branch to keep (`RecallView.source`), and the core reads, renders and ranks them (op `search-sessions`). So is a whole recall call (`recall()` in `src/core/recall-run.ts`, op `recall`, when the call carries its raw params or text, `RecallInput.call`, as the tool and the command pass them): `lisp/src/request.lisp` (the tool's params repaired and the command's text parsed, the Ignored: note, both surfaces' hints, the output format), `sessions.lisp` (the project's other sessions; the files themselves, newest first, come from the TS side, since SBCL reads modification times to the second) and `recall.lisp` (the views, every action, expand's full view, #N:path, mode:'touched', the cap). So is what a compaction does (`planCompaction` in `src/compaction/plan.ts`, op `compact`): `lisp/src/compaction.lisp` (the live window, the cut, its token-budget rescues, the running-turn and whole-window cuts, smart keep-tail, the summary input, [History Index], the readers of an earlier compaction's details, pins and state, the growth guard, the stats) and `working-set.lisp`. So are the window rules (`src/core/window.ts`): `lisp/src/window.lisp` (each host's trigger from the policy it hands the hook, a recovery's bound, the budgets below the trigger, and the context's overhead and chars per token, which `planCompaction` sizes from first, `sizeCompaction`, so the plan carries its `sizing`; the limit an overflow error states and the trigger `window-limits.ts` checks once a run settles, op `window`); the learned-limits file and the effective window stay in TypeScript (`model-limits.ts`: file IO). The hook (`src/hooks/compaction.ts`) gathers the inputs (the host's rule, policy and window, its count of the context, settings, `#N`) and acts on the plan; the one thing the core cannot do is the host's `convertToLlm`, so `plan.ts` sends, with each branch entry, what `toSummaryMessage` makes of its live message and of the original omp-vcc kept of it (`hostNotes`). The summary (`compileSummary`, op `summarize`) is the core's too: `lisp/src/blocks.lisp` (sanitize, host noise, normalize, a block's command and files), `extract.lisp` (the section extractors), `brief.lisp` (the brief and its ranking), `summary.lisp` (render, the stored state and its merge, the legacy reader, pin and history lines); the TS pipeline's regexes are written there as the TS writes them (`rx.lisp`, on the same engine). Words are counted with SBCL's UAX #29 segmentation, which agrees with Intl.Segmenter except in scripts ICU segments by dictionary (Han, kana, Thai, Lao, Khmer, Myanmar): a window with such text is left to the TS pipeline (`left-to-ts`). Regex queries and terms run in `lisp/src/regex.lisp`, JavaScript's non-unicode `/i` dialect: its syntax errors (on which safeRegex searches the text literally), matching on UTF-16 code units, case folding by the spec's Canonicalize (`+canonical+` in `js-string.lisp`, which the term search folds by too), and the 3 s budget; a construct it would not be sure to read as JavaScript does (named groups, legacy octal escapes, a capture in a look-behind) is refused, and that query runs in TypeScript. The hosts load only JS/TS extensions, so `index.ts` and `pi.ts` stay TypeScript and hand requests to the core: one JSON object on its stdin, one on its stdout (`lisp/src/server.lisp`), run with `spawnSync` from `src/core/lisp-core.ts`, which is why CI's import check allows `node:child_process`. The core is used when `OMP_VCC_CORE` names its executable; any failure (none set, a crash, a query it leaves to TS such as a regex) runs the TypeScript code instead. `sbcl --non-interactive --load lisp/build.lisp` dumps it to `lisp/build/omp-vcc-core` (git-ignored; ~40 MB, links only libc and libm, starts in ~5 ms). It has no dependencies but SBCL: JSON (`lisp/src/json.lisp`: false, null and `[]` read as `:false`, `:null` and `#()`, never `NIL`) and the test runner (`lisp/test/support.lisp`) are its own, and session text is never given to the Lisp reader (`read` interns into any package a `pkg::` names). Lengths, cuts and offsets are JavaScript's, in UTF-16 code units (`lisp/src/js-string.lisp`), so every budget is the same number on both sides. Lisp tests: `sbcl --non-interactive --eval '(require :asdf)' --eval '(push (truename "lisp/") asdf:*central-registry*)' --eval '(asdf:test-system "omp-vcc-core")'`. `tests/lisp-core.test.ts` builds the executable with the `sbcl` on PATH (or `SBCL`) and compares it with the TS code hit for hit over generated sessions, `tests/lisp-regex.test.ts` compares compile errors, `test`, `search` and global match counts with JavaScript's own over 1,500 generated and 70 hand-picked patterns (and targeted ones for captures and back-references), `tests/lisp-recall.test.ts` compares 600 generated tool and command calls over generated projects (and calls aimed at each session's writes) with recall()'s output, asserting the core answers nearly all itself, `tests/lisp-compaction.test.ts` compares the whole plan of 150 generated branches (earlier compactions, /clear, custom messages, branch summaries, pins, kept originals, every keep, reason and budget) and of swept edge cases (the oversized-tail factor, the growth guard's share, a first request over the budget, files competing for [Working Set]) with planCompaction's on omp's convertToLlm, `tests/lisp-window.test.ts` compares the overflow limits, triggers, policies and budgets of generated windows, policies (malformed ones too), context counts and overheads with window.ts's, `tests/lisp-summary.test.ts` compares the text, stored state and sections of 100 generated compactions (every message shape, four chained per session, some from a legacy or foreign summary's text) and of older summaries' formats with compileSummary's, asserting the core answered each itself, `tests/lisp-session.test.ts` compares every entry it reads from generated session files (every message shape, malformed entries, branches, forks, kept originals) with load-messages.ts on every branch filter, and the omp and Pi host tests run recall through it in a real session; each skips without SBCL. CI runs the suite again with `OMP_VCC_CORE` set, so every search goes through the core, and `OMP_VCC_CORE_STRICT=1`, under which a core failure other than a refusal throws instead of falling back (the Lisp tests set it too): a test must not pass on the TypeScript fallback.

## Layout

- `index.ts` (`omp.extensions` in `package.json`): `register(pi, ompHost(pi))`.
- `pi.ts` (`pi.extensions`): `register` on Pi's host, with `convertToLlm` and `getAgentDir` imported from Pi's own package (Pi's loader resolves it to the running Pi) and Pi's trigger from its `session_before_compact` (`reason`, `willRetry`).
- `src/host.ts`: the `Host` a binding uses: what differs between the hosts (`HostProfile`: name, command prefix, trigger rule, settle event, models file, whether it rewrites messages in place; `OMP_HOST`, `PI_HOST`) and the host's functions (`convertToLlm`, `agentDir`, `triggerOf`); `bind` (a profile with its config, and its `window(model)`); the compaction trigger and `isRecovery`; `compactAndWait`. `src/register.ts`: everything omp-vcc registers, the same on both hosts (raw capture only where the host rewrites in place), with a fresh compaction state per binding.
- `src/hooks/compaction.ts`: the compaction hook, shared by both hosts: the event in, the compaction (or a cancel) out. The host's functions and rule come in through a `CompactionHost`, and the branch is read through `src/core/context-edits.ts` (Pi's `context_edit` entries applied as Pi applies them; an omp branch has none). Under it, `src/compaction/`: `cut.ts` (which messages are live, where to cut, the token-budget and running-turn cuts, smart keep-tail; pure, given the host's `convertToLlm`), `summary-input.ts` (what each live message becomes in the summary, `toSummaryMessage`, the one path for the summary and the cut's render check), `assemble.ts` (the summary with its history, pins and working set, and the growth guard) and `stats.ts` (the outcome line and toast).
- `src/core/raw-store.ts` (the originals of what omp rewrites in the session file, in `<session>.jsonl.vcc-raw`) and `src/hooks/raw-capture.ts` (copies them from omp's entries as they land).
- `src/hooks/omp-host.ts`: omp's `Host` (`ompHost`): its `convertToLlm` and agent dir from `pi.pi`, and the trigger (reason, willRetry) read from `auto_compaction_start`, since omp's `session_before_compact` carries none.
- `src/core/window.ts` (pure: limits stated in overflow errors, each host's trigger from the policy it passes in `preparation.settings` as a `TriggerRule` (`ompTrigger`, a port of pi-agent-core's `resolveThresholdTokens`, which omp does not export; `piTrigger`, Pi's `shouldCompact`, the window less `reserveTokens`; `tests/window.test.ts` checks each against the host's own), `triggerFor` (the trigger a compaction sizes for), the budgets), `src/core/model-limits.ts` (the learned-limits file, with the host's policy kept beside a learned window, and the effective window, `windowOf`, which a binding reads as `window(model)`) and `src/hooks/window-limits.ts` (learning from `message_end`, compacting once the host settles (omp's `agent_end`, Pi's `agent_settled`) when its window is too high).
- `src/names.ts`: omp-vcc's own names (the tools, the pin entry and notice types, the recall command's message type, the compactor ids); whatever writes, matches or mentions one imports it.
- `src/core/tools.ts`: the one reading of a tool call (its kind, the files it works on, the command it runs, what it is about, the text it writes), by the names and arguments of omp's and Pi's own tools, and by shape for another extension's; nothing else matches a tool name or argument.
- `src/core/`: summary pipeline (`normalize` → `filter-noise` → `summary-state.ts` (this window's sections from `src/extract/`, merged into the state the previous compaction stored in `details.summaryState`) → `brief`/`rank` → `format.ts` (`renderSummary`, the only place summary text is written), driven by `summarize.ts`; `legacy-summary.ts` reads a previous summary that has no stored state, from its text, in a frozen copy of the format it was written in (a change to `format.ts` changes what is written from then on), and is the only place summary text is read), `history-index.ts` (`[History Index]`: built in the hook, stored in the compaction's `details.historyIndex`), `working-set.ts` (`[Working Set]`: chosen in the hook from the originals of what is summarized and what is kept, its `#N` in `details.workingSet`), recall (`recall-request.ts` parses the tool's params and the command's text into one request, `recall-run.ts` `recall()` runs it for both, each surface giving only its hint wording, `search-entries.ts` ranks, `touched.ts` is `mode:'touched'`), settings.
- `src/extract/`: one module per summary section (user messages and early requests, files, commits, tracked commands).
- `src/core/session-file.ts`: the session file as both hosts write it: what `#N` counts (`indexById`, `indexedMessages`), the header and the parent session, the active branch, omp's `/clear` boundary (`afterReset`), a scan by line heads for listing many files, and the host's session manager read through `hostBranch`/`hostEntries` (undefined where it has none or throws); `src/core/load-messages.ts` reads a file once per recall call for every view of it.
- `src/core/pins.ts` (pinned notes: `omp-vcc.pin` custom entries replayed along the branch) and `src/core/sessions.ts` (the project's other session files: listing, id resolution, each file's active branch).
- `src/commands/`: `/omp-vcc` (`omp-vcc.ts`, with `compact-feedback.ts`), `/omp-vcc-recall`, `/omp-vcc-pin` and `/omp-vcc-unpin`.
- `src/tools/`: `vcc_recall` (`recall.ts`) and `vcc_pin` (`pin.ts`): the text the agent reads, the JSON Schema, and what a call does.
- `src/details.ts`: what a compaction stores in its details (`compactor: "omp-vcc"`; `"pi-vcc"` is read too).

## Rules

- The code is the API: what omp-vcc relies on of a host comes from that host's own source, types and docs in its package, never a guess or another host's. omp and Pi share a lineage, so the shared modules are typed against omp's API and `pi.ts` hands them Pi's binding; where the hosts differ (trigger rule, trigger source, settle event, commands, what rewrites in place), the difference goes through `src/host.ts` or the `CompactionHost`, not a branch on the host's name in shared code.
- Support each whole peer range (omp `>=18.14.0`, Pi `>=1.0.0`; CI tests both floors and the latest of each). Raise a floor in `package.json` when a change needs a newer host; otherwise use a newer API only behind a check that keeps older releases on the old path.
- Nothing under `src/` or `index.ts` imports a package at runtime, omp's and Pi's included: types come from `@oh-my-pi/*` and `@earendil-works/*` with `import type`, omp's functions from `pi.pi`, and what a host's docs describe is ported (as `ompTrigger`, `piTrigger` and `applyContextEdits` are), not imported. `pi.ts` alone imports Pi's own package, as Pi's extension API has it (Pi's loader resolves it to the running Pi). CI checks that `bun build index.ts --target bun --packages external` imports nothing, statically or dynamically, but node builtins, and `pi.ts` nothing else but `@earendil-works/pi-coding-agent`.
- omp-vcc works with the host as configured: it never changes omp's or Pi's settings and never asks the user to. On Pi, every compaction asks the hook (`session_before_compact` with `reason` and `willRetry`), and the summary reads the branch as Pi's context holds it (its `context_edit` omissions and replacements applied), while recall reads the raw file; Pi never rewrites an entry, so nothing is kept aside. On omp: it never changes omp's settings (only omp's settings registry, a package import, can) and never asks the user to. Every omp method that writes a summary (`remote`, `snapcompact`, `handoff`, `soft`, the notes-backed rollover) asks the hook first, and the hook answers every automatic pass, recovery included (a running turn's newest steps kept, or the whole window summarized; cancelled with the reason only when no summary can shrink it), so none of them writes one. It steps aside only for the user's opt-outs (`overrideDefaultCompaction: false`, `skipForProviders`) and when nothing is live. omp's shake runs before it (an overflow, when shake is the first usable method) or after it (the post-commit rescue), and hands over through `soft`. What runs around it rewrites messages in place (shake, `supersedeReads`, `dropUseless`, the age-based prune), so omp-vcc keeps the originals as they land (`src/core/raw-store.ts`, `src/hooks/raw-capture.ts`, `keepOriginals`). Recall reads them for the entries omp rewrote (`prunedAt`, an `artifact://` splice), falling back along a fork's `parentSession` chain; the summary is written from them (the cut and budgets count what the context holds); and on omp's `context` event, omp's placeholder for a kept result gains ` (the original: vcc_recall expand:[N])`, the same text on every request so the prompt cache keeps it. The copy comes from omp's entries, not the event's message, which omp de-obfuscates for display. `tests/omp-host.test.ts` checks it in a real omp session.
- omp binds the factory again for every subagent session while module state is shared (Pi binds it per session runtime), so per-session state lives in the binding `register` builds (its `Config` from the host's agent dir, `createCompactionState()`, `createWindowState()`), never in a module variable.
- `#N` refs in summaries are session-wide entry indices that `vcc_recall` resolves. Any change to which entries are indexed must keep them stable; `[History Index]` ranges are `#N` too. Pins are `custom` entries, so they are never counted. In another session (`session:'id'`, `scope:'project'` hits) `#N` is that session's own.
- Sections carried across compactions are merged from the structured data the previous compaction stored (`details.summaryState`) or re-capped verbatim, never re-written and never parsed back from the summary text (only a summary with no stored state is, once, by `legacy-summary.ts`): rewriting a previous summary is how LLM compactors lose detail compaction after compaction. Keep the summary bounded as the session grows (the long-horizon test checks it). `[Working Set]` is not carried at all: it is chosen again at every compaction (the merge drops the previous one), within `compactionBudgets`' `workingSetTokens` and at most half of what the compaction removes. It picks by paths, failure flags, recency and recall's own ranking, never by wording.
- Agents act on recall and summary text (headers, hint lines, `Ignored:` notes). Treat it as an interface: change it on purpose, and update the tests that pin it.
- Session data written under the pi-vcc name stays readable: `compactor: "pi-vcc"` details, and `pi-vcc-config.json` (copied to `omp-vcc-config.json` once). On Pi the commands keep pi-vcc's names (`/pi-vcc`, `/pi-vcc-recall`, `/pi-vcc-pin`, `/pi-vcc-unpin`); the compactor id is `omp-vcc` on both hosts.
- The smart keep-tail limit (25k) is omp-vcc's own and does not follow omp's `compaction.keepRecentTokens`; it, the summary budget, the summary's section sizes (`summaryLimits`) and the growth guard's margin scale with the trigger (`compactionBudgets`), and `expand`'s clips with the recall cap (`expandDetailChars`). All must stay the old numbers on a ~128K window. A new size limit that depends on how much context there is belongs there too, not in a constant.
- omp-vcc makes no network calls. The window is the host's (`ctx.model.contextWindow`, which omp's discovery fills from the provider, and Pi's catalog and `models.json`) or a smaller limit an overflow error stated; omp-vcc does not ask providers itself.
- Tests that read settings set `OMP_VCC_CONFIG_PATH` to a temp file, never the user's config. `tests/real-sessions.test.ts` runs for each host whose sessions exist here (`~/.omp/agent/sessions`, `~/.pi/agent/sessions`), reading them with that host's own parser.
- `research/` is git-ignored local data (real sessions, replays). Never commit it or quote session content in commits or PRs.
- Note user-facing changes in `CHANGELOG.md` under `[Unreleased]`.
