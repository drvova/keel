# Changelog

All notable changes to `@drvova/omp-vcc` are documented in this file. Entries from 0.11.2 back are those of `@sting8k/pi-vcc`, which this is forked from, and describe it on Pi.

## [Unreleased]

### Breaking

- **SBCL is required** — omp-vcc's work (compaction, the summary, recall, pins, settings, raw capture) is done by a core written in Common Lisp (`lisp/`), which omp-vcc builds with the user's SBCL (`sbcl` on the `PATH`, or `SBCL`) the first time it loads: a few seconds, once for each version, into `lisp/build/` or `OMP_VCC_CORE_BUILD_DIR`. Install SBCL with the system's package manager (`apt install sbcl`, `brew install sbcl`). Until the core is built, or without SBCL, omp-vcc steps aside, says why once, and the host compacts as it would without it; `vcc_recall` and `vcc_pin` answer with the reason. `OMP_VCC_CORE` names a prebuilt core instead.

- **omp-vcc, native to omp and to Pi** — the project is now `@drvova/omp-vcc`, a fork of `@sting8k/pi-vcc` 0.11.2 that runs natively on [omp](https://github.com/can1357/oh-my-pi) (oh-my-pi), and on [Pi](https://github.com/earendil-works/pi) through an entry rewritten against Pi's own current API (see Changes): install with `omp install https://github.com/drvova/omp-vcc` or `pi install git:github.com/drvova/omp-vcc`. Pi's old tool bindings (TypeBox schemas, `prepareArguments`) and the invisible auto-continue for old Pi releases are removed, and the TypeBox peer with them; the peers are `@oh-my-pi/pi-coding-agent >=18.14.0` and `@earendil-works/pi-coding-agent >=1.0.0`, both optional, with no upper bound (both release often; CI tests each floor and the latest of each every week). On omp the extension uses omp's own types and, at runtime, only the functions omp hands it (`pi.pi`), and the tests run against omp's real `convertToLlm`, session parser and a real omp session.
  - The repository is [drvova/omp-vcc](https://github.com/drvova/omp-vcc); GitHub redirects the old `drvova/pi-vcc` URL. It is installed from GitHub only, not npm.
  - On omp the commands are renamed: `/omp-vcc`, `/omp-vcc-recall`, `/omp-vcc-pin`, `/omp-vcc-unpin`. On Pi they keep pi-vcc's names (`/pi-vcc`, …). The tools keep their names (`vcc_recall`, `vcc_pin`).
  - The config file is `omp-vcc-config.json` in omp's agent directory (`~/.omp/agent`, or the profile's); a `pi-vcc-config.json` there is copied over on first load. `OMP_VCC_CONFIG_PATH` replaces `PI_VCC_CONFIG_PATH`, and the debug snapshot is `/tmp/omp-vcc-debug.json`.
  - `continueAfterThresholdCompact` is removed: omp resumes the run itself after automatic compactions (`compaction.autoContinue`). An existing config keeps the key; it is ignored.
  - Compactions are stored with `compactor: "omp-vcc"`. Those pi-vcc stored on omp (`"pi-vcc"`) are still read as this extension's: their `[History Index]` carries on, and their stats toast and follow-up prompt still fire.
  - Toasts say `omp-vcc:`; pinned notes are `omp-vcc.pin` entries.

### Added

- **Undo the last context edit** — `/omp-vcc-evict undo` and `vcc_context {undo: true}` reverse the last eviction or restore, every run it made; an undo again does it again. The benchmarks also report the prompt tokens the provider read uncached, the cost every edit of the context adds.

- **Named notes carry into the next session, and the user's stay the user's** — a new session (a restart, `/new`) starts with the named notes of the project's last session, marked with the session they came from (`(agent, from session 01a194d8)`), and is told so; unnamed notes stay with their session. The agent can no longer define again or unpin a note the user pinned: it is told the note is the user's and to ask, or to pin its own under another name.

- **Evictions that pay** — the agent's `vcc_context` drop is refused when it frees less than 45% of what it makes the provider read again uncached (everything after it), which a smaller context would repay only after many requests; the answer names the run from the oldest end that would pay (`oldest:4`). The user's command and the automatic eviction are not checked.

- **Turn numbers in view** — with `vcc_context` there, each request in the context starts with its turn's `#N` (`[#12]`), the same on every request, so the agent takes turns out by number without listing them first.

- **One core process per session** — instead of a process per request, one core stays up for the host and answers every request (0.4 ms a request, against 5 ms for a process start), and keeps the session file it read parsed, reading only the lines it gained since, with what recall works out of each entry (its rendering, the text search reads, folded): a recall over a 20 MB session takes 0.5 s, from 1.6 s. It ends with the host or after 5 minutes idle; a core that dies is replaced; on Windows, or with `OMP_VCC_CORE_LIVE=off`, each request runs its own process as before.

- **Named notes, defined again in place** — a pinned note can have a name (`vcc_pin` `name`, or `/omp-vcc-pin name:auth-plan …`); pinning that name again replaces its note, and `unpin` takes the name, so the agent keeps a plan, a decision or a command current under one name instead of piling up notes that go stale. With eviction on (or anything out), the pinned notes stand first in every request, in one block as they read now, so a note stays in view whatever turn it was pinned in has left; the block changes only when a note does. `vcc_context` lists every pinned note.

- **Eviction says what the turns did, and reaches the running turn** — the line in place of evicted turns names the files they changed, their commits and failed calls, from the originals omp-vcc kept, so it points at them as `[History Index]` does and reads the same on every request; a `vcc_context` note shows as the agent's. As the context fills, the running turn's older steps leave after the finished turns, keeping its request and newest step, so a single long turn on a small window no longer leaves eviction nothing to take. Past half the trigger the model is told how full its context is, once per tenth and only while something can leave, as a stored message so the prompt cache keeps it. The line rides on an adjacent message the provider reads as the user's (or a tool result), so a request never holds two user messages in a row; a steer the user sends mid-run on omp (which marks it) is part of the running turn. The size note waits for the next turn instead of steering the running one, starts again from half after a compaction or after the agent or user takes turns out, and an eviction never records again what is out already.

- **Turns out of the context, whole** — the other way to make room: old turns leave the requests the host sends, whole, never summarized or rewritten; the session file keeps every word, and `vcc_recall expand:[N]` reads them back. `/omp-vcc-evict` (`/pi-vcc-evict` on Pi) takes out the oldest half, a number of turns, all finished ones or a `#N` range, brings them back with `restore`, and lists what is in and out. With `"evict": true`, the agent gets `vcc_context` to decide itself, past 85% of the host's trigger the oldest finished turns leave by themselves, down to half of it, and the host's automatic threshold and idle passes are turned down while a finished turn is left to take out (with none left, a recovery, or a compaction the user asks for, the summary runs). One line naming their `#N`, their requests and how to read them back stands where they were, the same on every request so the prompt cache keeps it. The ledger is `omp-vcc.evict` custom entries along the branch. The idea is Context Language Models (arXiv:2609.37725) and nodecode's eviction.

- **`[Task State]`** — every summary says where the work stands, after `[Pinned Notes]` and in the same shape at every compaction: the latest request, how many tool calls followed and how many failed, the files they changed, the last result, and the failure no later run of the same call fixed, each with its `#N`, so the agent reads where it is instead of spending requests re-reading files or re-running checks to find out. It is read off the transcript by rule and built again at every compaction, never carried; it costs about 70 tokens. The idea is the papers' separate task state (HyMem, arXiv:2608.15703; Context as a Tool, arXiv:2512.22087), whose models write it.

### Changes

- **Pi, natively** — `pi.ts` (`pi.extensions` in `package.json`) runs omp-vcc on Pi 1.0 and later, written against Pi's own code: Pi's `convertToLlm` and agent directory come from Pi's package as Pi's extension API hands it (Pi's loader resolves it to the running Pi), and everything else is the shared core omp uses, with what differs between the hosts passed in:
  - **Pi's trigger** — Pi compacts past the window less `compaction.reserveTokens` (its `shouldCompact`); Pi hands its settings to every compaction, and omp-vcc sizes the summary, the kept tail and `[Working Set]` for that, as it sizes them for omp's own threshold on omp. The trigger comes from Pi's event (`manual`, `threshold`, `overflow`, and whether Pi retries the turn), and `details.limits.windowSource` is `"pi"`.
  - **Pi's context edits** — Pi never rewrites the session file; it changes what the model sees with `context_edit` entries (it omits a failed attempt before an overflow retry; an extension may redact a result). The summary reads the branch as Pi's context holds it, omissions left out and replacements applied, exactly as Pi's own projection does (checked against Pi's `buildSessionContext`); `vcc_recall` still reads the raw history.
  - **A window Pi overestimates** — when an overflow error states a smaller window than Pi uses, omp-vcc compacts at its own trigger once Pi's run has settled (`agent_settled`, not after a run the user aborted), and says how to set the window in Pi's `models.json`.
  - **`/pi-vcc` waits for Pi** — Pi's `compact()` returns before the compaction runs; the command hands Pi its instructions and waits for Pi's callback, so the stats toast and the follow-up prompt come after the summary, not before.
  - Tested in a real Pi session built with Pi's own SDK (commands, tool validation, the automatic threshold and overflow paths, context edits, pins, recall across the project's sessions), on Pi 1.5 and on the 1.0 floor, and through the hook on Pi's own `convertToLlm` with Pi's message roles and `edit` shape. The real-session test reads `~/.pi` sessions with Pi's parser, and the real-model benchmarks run in either host (`--host=pi`, `OMP_VCC_LH_HOST=pi`).
  - The suite runs each test file in a fresh module registry (`bun run test`): omp answers Pi's package names with its own once it is loaded in a process, so a Pi test after an omp one would have tested omp's copy; each Pi test now checks it has the real Pi.

- **Limits follow the model's context window** — the kept tail, the smart keep-tail trigger and the summary budget were fixed numbers (25k, 5k, 1.1k–2k tokens) whatever the model; they are now shares of where omp compacts, clamped as the `vcc_recall` cap already was, so what a compaction keeps lands inside omp's recovery band. On a ~128K window nothing changes; a small window keeps less (a 25k tail there left omp re-compacting or shaking tool output), a ~1M one allows a summary up to 3.4k tokens. The window is omp's, or a smaller limit an overflow error stated, kept in `omp-vcc-models.json` for later sessions; omp-vcc makes no network call of its own. When that is below omp's window, omp's trigger cannot fire before an overflow, so omp-vcc compacts at the end of a run past the real window's trigger, and says so once. Each compaction records the window and trigger it sized from in `details.limits`. What a compaction cannot remove (system prompt and tool schemas) is measured from the session's first request, which held little else; the chars-per-token estimate is calibrated on the messages alone. Tested with a real model behind a provider with a 40K window that omp was told was 128K: the limit from its overflow error set the trigger to 23,616 tokens, and omp-vcc compacted when a run ended past it.
- **Recall keeps what omp rewrites, with nothing set in omp** — between compactions omp keeps the live context small by rewriting messages in the session file: it blanks old tool output (`[Output truncated - N tokens]`), reads a newer read supersedes and results their tool flagged useless, and shakes tool output and large fenced blocks into `artifact://` files (on an overflow, before omp-vcc is asked). `vcc_recall` reads the session file as the raw history, so each rewrite lost what it replaced: a search for an error message in old tool output found only the placeholder. omp-vcc now keeps the original of every message omp may rewrite, copied from omp's own entries as they land (secrets stay obfuscated as in the session file), in `<session>.jsonl.vcc-raw` beside the session, and recall searches and expands the original of each entry omp rewrote. omp's settings need no change: every omp method that writes a summary asks omp-vcc first. `keepOriginals: false` turns the copy off.
  - **omp's placeholder says where the original is** — to the agent, `[Output truncated - 1200 tokens]` read as output that was gone, and it ran the tool again to get it back. Before each request, a placeholder omp wrote over a tool result whose original omp-vcc kept now ends with ` (the original: vcc_recall expand:[12])`. Only the request changes, not the session file, and the text is the same on every request, so the provider's prompt cache keeps it.
  - **The summary is written from the originals** — a compaction after omp blanked a tool result summarized omp's placeholder, so a commit whose `git` output was blanked never reached `[Commits]`, and a failure's output left the transcript. The summary and `[History Index]` now read the kept originals; the cut and the budgets still count what the context holds.
  - **A fork reads its parent's originals** — a fork or branched session carries its parent's entries as they were, some already blanked, and started a store of its own. Recall now falls back along the session's `parentSession` chain.
- **The compaction brings back what the next step works from (`[Working Set]`)** — a summary says what happened, but the next step needs what the agent was working from: the file it is changing, the output of the call that just failed. A compaction took those out of context, and the agent spent its next requests reading them again. Each compaction now ends its sections with `[Working Set]`, quoted from the originals omp-vcc keeps:
  - the latest version of each file the work is on (touched by the kept messages, named in the latest request, or read or changed since the request in progress began, most recent first), unless the kept messages already hold a read or write of it. It is looked for in the whole session since `/clear`, not only in what this compaction removes: in real sessions most of the files an agent read again after a compaction were read before an earlier one. What showed the file last comes first, newest first (omp's edit result is the changed lines with their numbers, a range read keeps its selector, `read "src/money.ts:60-100"`), then its last whole read. A file comes back whole or as those lines, never as its first lines: in real runs, after part of a file came back the agent read it again anyway;
  - the output of the latest failed call that no later run of the same tool on the same path or command fixed, by its end, where the error is;
  - up to 3 results `vcc_recall` ranks highest for the latest request, a file's latest read only, and not the agent's own edits.

  Each excerpt ends with the `vcc_recall expand:[N]` that shows the rest, and `details.workingSet` lists the `#N` it brought back. It takes up to 3,800 tokens on a ~128K window; on a smaller one, 14% of the trigger, out of what the compaction may land with above the kept tail's 1,000-token floor, so it never pushes a compaction past where omp expects it to land (2,090 on a 40K window with omp's system prompt and tools, none on a 32K one); more past a 500K trigger (6,460 on a 1M window), out of the kept tail's room, which stays 25k there, and never more than half of what the compaction removes; with `workingSet: false` that room goes to the kept tail. It is chosen again at every compaction, never carried, so the summary stays bounded. On the long-horizon benchmark, run by omp itself, the facts, pointers and recall are the same with and without it on a 32K, 128K and 1M window; it adds about 0.7k chars to the final summary on 128K and 1M, and up to 7k on 32K. (That session's scripted agent does not read the summary, so the benchmark cannot show what it saves; the real-model runs below can.) `workingSet: false` turns it off.

  Tested with a real model (DeepSeek V4.1 Flash) on a five-step task in a 40K window, where omp compacts 2 to 4 times per run, 4 runs with the working set and 4 without: all 4 with it finished every step and every test; without it, 3 runs had a step run out of time and one ended with a failing test. Re-reads after a compaction and requests were about the same (18 and 13 re-reads in 12 compactions each; 195 and 199 requests): on a 40K window the working set has about 3k chars, too few for whole source files, so the agent read them again. On a ~128K window it has about 13k. With the working set, the agent edited a file from the lines it brought back, without reading it again, 4 times. After these runs the working set got 14% of a small window's trigger, from 3.5%, and the files of the request in progress: replayed over the 41 compactions of the last two batches, it would have held 14 of the 73 files the agent read again whole, from 1.
- **The trigger is omp's own** — omp-vcc sized every compaction for where it assumed omp would compact next: omp's default policy on the window, or the context a threshold pass had just measured. omp hands extensions its compaction policy for the model with every compaction (threshold percent or tokens, reserve, the model's `compaction.modelThresholds` entry), and omp-vcc now applies it as omp does (a port of omp's `resolveThresholdTokens`, tested against omp's own over every policy shape). A user who compacts at 60% on a 1M model now gets budgets for 600K, not 850K. When the real window (from an overflow error) is below omp's, the user's policy applies to the real window; and with omp's automatic compaction turned off (`compaction.enabled: false`), omp-vcc no longer compacts on its own at the end of a run.
- **The summary's sections follow the window too** — the user messages (15), files per category (10), commits (8), `[History Index]` lines (8) and brief lines (120) a summary keeps were the same on every model. They are still those numbers on a ~128K or 200K window; below it they shrink with the square root of the trigger (a 32K window keeps about 40% of each, never less than a quarter), and past a 500K trigger they grow as the brief's ceiling does (1.7× on a 1M window). `[Early Session Requests]` and pinned notes do not scale. `details.limits.summaryScale` records the factor when it is not 1. On a 120-turn test session compacted every 6 turns, a 32K window's summary is half the size (3.6k chars, from 7.5k) with the same pointers and recall, and a 1M window's holds 4 of the 7 planted facts instead of 2. `scripts/benchmark-long-horizon.ts` takes a window (`all` runs 32K, 128K and 1M).
- **Pinned notes** — `/omp-vcc-pin <note>` (and the agent's `vcc_pin` tool) pins a note that stays verbatim at the top of every summary, as `[Pinned Notes]`, until `/omp-vcc-unpin <N>`. It is for what holds for the whole task and would otherwise age out: a decision and its reason, a constraint, a fact the work depends on. Notes are stored as omp-vcc entries in the session file (not in the model's context, not counted in `#N`), follow the branch they were pinned on, and start over after `/clear`. Pinning from the command also tells the agent on its next turn. A pin made at turn 9 of a 120-turn session is still in the summary after 20 compactions.
- **Recall across sessions** — `vcc_recall` reaches this project's earlier sessions (the other session files in the same directory: restarts, `/new`, forks, handoffs and moves): `mode:"sessions"` lists them newest first with their pinned notes, `scope:"project"` makes a query search them too (the 20 newest, up to 24 MB, ranked together; a hit says `[session <id>]`), and `session:"<id>"` runs any call inside one, on its own active branch. `/omp-vcc-recall` takes `sessions`, `session:<id>` and `scope:project`.

- **Native to omp** — pi-vcc reached omp only through omp's Pi compatibility layer. Now:
  - `/omp-vcc`, `/compact` and every automatic compaction (threshold, overflow, idle, cut-off reply) go through omp-vcc. Through the compatibility layer, `/pi-vcc keep:N` lost its keep count and its marker, because omp's `ctx.compact()` options have no `customInstructions` (with `overrideDefaultCompaction: false`, omp's own LLM summary ran instead), and in print/RPC mode a failed compaction became an unhandled promise rejection.
  - The summary records why it ran (`reason` also takes `idle` and `incomplete`, read from omp's `auto_compaction_start`), and omp-vcc answers every automatic pass itself, so omp's own summarizers (snapcompact, handoff, server compaction, an LLM summary) never write one while it compacts (see Fixes).
  - `vcc_recall` and `vcc_pin` are top-level tools with read-only approval (omp otherwise puts extension tools behind discovery and asks before running them). omp checks arguments before an extension sees them, so the schema accepts the loose forms agents send and the tool repairs them itself.
- **omp session content is summarized as it is meant** — after `/clear`, the summary covers only what follows it, as omp's own compaction does. A python cell the user ran is one `>>> code (#N)` line, like a `!cmd`. omp's host reminders (developer messages) and the bodies of `@file` mentions are left out. Text an extension sent on the agent's behalf is not read as a user message. In `vcc_recall` these show as `[python]`, `[file]`, `[developer]` and `[custom]` entries instead of empty assistant ones.
- **omp's edit and read tools are understood** — files changed by omp's hashline `edit` (`[path#TAG]` sections) appear in `[Files And Changes]`, in the transcript and in `mode:"touched"`, and a file read with a line selector (`src/a.ts:50-100`) is listed once, without it.

- **Long tasks keep their bearings** — measured with a new long-horizon benchmark (`scripts/benchmark-long-horizon.ts`): a 60- or 120-turn session with facts planted at known depths, compacted every 6 turns. Before, the final summary held none of the 7 facts and pointed at none, and a reworded `vcc_recall` query found 6. Now the summary keeps 2–3, points at 5, and recall finds all 7, while the summary stays bounded (about 7.4k chars at both lengths, from 5.7k). In a test with a real model on such a session, the old summary led it to answer that no test had ever failed; the new one led it to the failure with one recall.
  - **`[History Index]`** — a new section, one line per compacted range of `#N` entries back to the start of the session: requests (the longest one quoted), the files or directories changed, commits, failed calls. It is built from the messages and stored in the compaction's details, never re-read from summary text, and stays at 8 lines: the adjacent ranges spanning the fewest entries merge. Older work that has left the other sections is still named there, so the agent knows which range to read or what to search for.
  - **Failed calls say so** — a tool call whose result was an error ends with `[failed]` in the transcript (a user-run `!cmd` with a nonzero exit too), and ranks higher, so it stays in the transcript longer.
  - **`vcc_recall` finds other forms of a word** — `rounding` finds `rounds`, `failure` finds `FAIL`: a plain English word of 5+ letters also matches its stem at the start of a word.
  - **Smaller recall results on small models** — one result is capped at a tenth of the model's context window when that is under 50 KB (at least 8 KB), so recalling one large entry cannot push a small window back over its compaction threshold.

### Fixes

- **The debug record goes beside the config** — with `debug` on, each compaction's decisions are written to `omp-vcc-debug.json` next to `omp-vcc-config.json`, not to a fixed `/tmp/omp-vcc-debug.json` that every session and subagent shared and overwrote.
- **A compaction's outcome line belongs to that compaction** — the line omp-vcc tells after a compaction is the one of the compaction the host applied, matched by its summary; a pass the host did not apply, or one another extension's compaction replaced, leaves nothing behind for a later one.
- **The core's build is tried again** — without SBCL, or after a failed build, omp-vcc said so for the rest of the session; it now tries again a minute later, so installing SBCL takes effect without a new session. A session waiting on another session's build no longer runs `sbcl --version` on every event.
- **A message the host refuses is told** — when the host would not send `/omp-vcc`'s or `/compact`'s follow-up prompt, a pin's note to the agent or `/omp-vcc-recall`'s result, omp-vcc dropped it silently; the user is now told what was not sent.
- **A search too deep for the stack says so** — a regex query that ran out of stack was reported as past the 3,000 ms budget; it now says the query is too deeply nested.
- **A `[History Index]` range never says `last undefined`** — a range read from an older index that counted commits it did not list said `2 commits, last undefined`; it now says `2 commits`.
- **`[Working Set]` and `[Task State]` agree on what failed and what was asked** — both now read the calls, their results, the open failure and the latest request one way. `[Working Set]` stopped at the newest failure, so when that one was fixed an earlier failure nothing fixed was left out; it now brings back the newest failure still open. Its latest request, like `[Task State]`'s, leaves out the host's injected `<system-reminder>` text and messages another extension sent in the user's name.

- **Tool calls read by the hosts' own tools** — the summary and recall each kept their own list of tool names, some from neither host (Claude Code's `file_path`, Factory's `TodoWrite`), and none had omp's `ast_edit`. One reading of a call now serves them all, by the names and arguments of omp's and Pi's own tools, and by shape for another extension's tool. What it fixes:
  - A search shows its pattern: the brief said `* grep "src"` and recall `grep(path=src)` for every grep, and kept only one of a turn's greps over the same directory; now `* grep "authRetry"`, one line per pattern.
  - `[Commits]` and tracked commands read the commands the user ran themselves (`!git commit -m …`, `!docker …`) and Pi's `powershell` tool, not only the agent's `bash` calls.
  - A commit's hash comes from its own call's output: with several calls in one message, a call was paired with whichever result sat next to it, and the hash was lost.
  - omp's `ast_edit` and apply_patch edits list their files as changed (in `[Files And Changes]`, `mode:'touched'`, `[Working Set]`), also when the session stores the edit under the name GPT-5 calls it by (`apply_patch`); they counted as some other tool's call.
  - `[Working Set]` reads omp's `:-20` (the last lines) and `:L50-L60` as part of a file, not the whole of it, names a search by its pattern, and offers only the latest run of a repeated call (the same grep three times was three items).
  - Drilling into an edit that only deletes text (`#N:path`) shows what it removed, not "no file content".
  - The brief no longer reads a markdown bullet in the agent's text as a tool call: two identical `* tests pass` lines were merged into `(#1, #2) x2`, and bullets counted toward a turn's eight calls.
- **Carried sections are merged from data, not re-read from the summary's text** — each compaction parsed the previous summary back into its sections, and the text did not always say what had been written: a path with a comma was split in two, a path long enough to wrap was listed twice after the next compaction, and the same absolute path was listed under two names once compactions had trimmed it against different directories. A compaction now stores its sections in its details (`summaryState`), and the next one merges into them item by item. A summary with none (written by pi-vcc, or by omp-vcc before this) is still read from its text, once. Such a summary listed absolute paths without the directory they shared, so the first compaction after upgrading listed a file touched again under two names (`f3.ts, /repo/src/f3.ts`); a listed path that one of the new window's full paths ends with is now that file. Also:
  - `[Working Set]` excerpts are no longer wrapped at 120 columns: an item shows a file's lines as they are.
  - The brief's `...(N earlier lines omitted)` counts every line it leaves out: it missed the ones dropped to start at a block.
  - `details.sections` names the summary's sections; it listed the brief's `[user]` and `[assistant]` blocks too.
- **Two sizes that did not follow the window now do** — the ranked brief took at most 80 blocks on any window, so the larger brief a very large window allows (up to 3.4k tokens on ~1M) could not be filled; the block cap now grows with it. `[Tracked Commands]` kept 10 invocations per command on every window; it now scales like the other sections (10 on ~128K, never under 3). Nothing changes on a ~128K window.
- **Recall inside an earlier session, and other recall fixes** — reading an earlier session (`session:'id'`), the follow-up calls recall suggested for a clipped result or clipped arguments, a touched file's content, an ambiguous file path or the next lines of a file left out the session, so they read the current one; they carry it now. After a search that reached edited or retried branches, `Read around a hit` put `scope:'all'` on the full-text call only, so the range it suggested left out the hit; both calls carry it now, inside an earlier session too. `/omp-vcc-recall` takes the quoted forms recall's own output shows (`session:'01a1…'`, `scope:'all'`), and a param sent empty (`scope: ""`, `range: []`) is not sent, rather than named under `Ignored:` on every call; `vcc_pin` reads one the same way (`unpin: ""` beside a note refused the pin). The next page of `mode:'touched'` keeps `scope:'all'`, and a call into an earlier session finds it by the files' headers instead of reading the 50 newest whole. Sessions started within a minute of each other shared a short id (omp's ids begin with the start time), so `mode:'sessions'` listed both under one id that named neither; a short id is now as long as it needs to be to name one session. The next page of a `scope:'project'` search said `page:2` without the scope, and of `mode:'touched'` without the mode, so following either read something else; a `mode:'touched'` page past the last came back empty instead of saying so. `/omp-vcc-recall sessions` points at its own next page, and `/omp-vcc-recall … scope:project` no longer ends a hit from an earlier session with the tool's syntax, and `#99:file` for an entry that does not exist says only that, not also that the current path has nothing. A session id older than the 50 newest sessions now names its session (`mode:'sessions'` says when there are more). A query whose match was only its word's stem showed no snippet; it shows where it matched. A search that ran out of time came back as a tool error, and could do so from inside a compaction's `[Working Set]`; it says so as its result. `#N:path:full` is capped at the recall result's size (it held 50 KB counted in bytes whatever the window), and says which line to read on from; that line no longer falls off the end of the result when the file fills it. `mode:'sessions'` shows a Pi session's `/name`, and a search with no hits counts the project's other sessions from their first lines instead of reading each file whole. A failed write of kept originals (a full disk) is tried again, not given up.
- **`vcc_recall` says why it ignored a param** — the reason given was the action's, so a `scope:'project'` dropped next to `session` read `Ignored: scope ().`, and on the command it was dropped without a word. Each ignored param now carries its own reason, on the tool and on `/omp-vcc-recall` alike; a negative index is named as not one, like any value recall cannot read; a call with an empty query no longer says `Found 25 matches for "   "`; and the tool's text says a session id takes 4 characters, as it does, not 8.
- **Why a compaction was not written reaches print and json modes** — omp-vcc's reasons (too few messages, a summary that would be bigger than what it replaces) went to the host's notify, which those modes drop, so only `/omp-vcc` said why there. They go to stderr there for every compaction, as the commands' output does, and so does the outcome line of an automatic pass or `/compact` (`omp-vcc: kept …`), which only `/omp-vcc` printed there, and the notice that a model's window is smaller than the host's.
- **`vcc_pin` names Pi's command on Pi** — its description told the agent that the user pins with `/omp-vcc-pin`, a command Pi does not have; on Pi it says `/pi-vcc-pin`.
- **An earlier session's pins are those of its active branch** — `mode:'sessions'` replayed every pin in another session's file, so a note pinned on a branch that was later edited away was still listed. It now replays them along that session's own branch, as the current session's are.
- **Summary sections after a failed edit, another compactor, or similar commands** — a failed read was listed as Read, and counted later as proof the file existed; a failed edit was listed as Modified, and on omp a failed write too (omp's own file list counts calls whatever their result; it now only fills in files the transcript does not show). After a summary another compactor wrote (an LLM's, say after `skipForProviders`), the next requests were kept as `[Early Session Requests]` for the rest of the session, and the compaction after that opened the slots again; the stored state now keeps how many are left. Its long lines are now wrapped like omp-vcc's own when carried; they were carried as written, up to thousands of characters a line. Two `[Tracked Commands]` invocations sharing their first 80 characters were stored clipped, shown as the same line twice, and merged into one at the next compaction; they are stored whole and clipped where shown.
- **No compaction in the host's stead before its policy is known** — where the host's window is too high, omp-vcc compacts at the end of a run, unless the host's policy says the user turned automatic compaction off. That policy was known only once a compaction in the same session had carried it, so every new session compacted for a user who had turned it off. It is now kept beside the learned window (`omp-vcc-models.json`), and until one is known omp-vcc does not compact on its own. A compaction it starts on a policy the user has since turned off, or past a threshold they have since raised, is cancelled by the policy that compaction carries.
- **`skipForProviders` holds at the end of a run too** — when omp-vcc compacts on its own because the host's window is too high, it checked `overrideDefaultCompaction` but not `skipForProviders`, so for a skipped provider it started a compaction the host's own compactor then ran, and said omp-vcc compacts there. Both checks are now one.
- **A switch in the config means what it says** — the config's values were copied over the defaults unchecked, so `"debug": "no"` (a string, so true) turned debug on. A switch now takes a boolean, or `"true"`/`"false"` in quotes; any other value leaves the default.
- **A refused pin is not a pin in the brief** — a `vcc_pin` call with both a note and `unpin` is refused, and the brief no longer shows it as pinning the note.
- **A second page of recall is its own brief line** — the brief named a `vcc_recall` call by its query, range, expand, mode, scope and session, not its page, so page 2 of a search merged into page 1 as `x2`.
- **A branch's summary is not a request** — on returning from a branch, the host's `Branch-return summary:` message took one of the three `[Early Session Requests]` slots, kept for the rest of the session, and `[History Index]` counted and quoted it as the user's request. It stays in the transcript and is left out of both, as an extension's message is. Also, a window whose only text before the cut is a host `<system-reminder>` is no longer summarized into an empty summary.
- **Smart keep-tail honours `skipCustomTypes`** — when the live window opened with a custom message the user skips, smart keep-tail measured the tail without the skip and grew to keep every turn; the cut then found nothing to summarize before it and fell back to summarizing the whole window, keeping only the final reply. It now measures as the cut does.
- **A request that mentions certain phrases is no longer dropped** — the summary left out any user message containing `Continue from where you left off.`, `No response requested.` or a TodoWrite reminder (strings from pi-vcc's old auto-continue and other agents), so `Continue from where you left off. Also fix the login` vanished from `[User Messages]`; and it cut `<ide_opened_file>` and other editors' tags from what the user wrote. Only omp's `<system-reminder>` blocks are cut now; the user's words are kept.

Found by running omp-vcc on omp with a real model:

- **omp's edits are read as edits** — omp's `edit` tool replaces text with `old_string`/`new_string`; omp-vcc knew only Pi's `oldText`/`newText`. So `vcc_recall mode:"touched"` left those edits out, and `[Working Set]` took them for reads of the file: a file the kept turn was editing counted as already in context and was never brought back. They are now changes like any other.
- **`[Commits]` lists only commits that happened, with their real hashes** — for a single commit, the first hash-looking text in the output was taken as its hash: a random number the same command printed on its own line, or hex inside a file path in a traceback. A commit in a command that failed before reaching it (`python3 tests.py && git commit …`) was listed though it never ran, and after `git commit --amend` the old hash stayed. A hash now comes only from git's own output: `git commit`'s `[branch hash]` line, a `--oneline` line naming the subject, a push range, or a line that is only a hash (with a letter in it). A failed command's commit counts only when git printed that it made it, and an amend updates the commit it replaces.
- **`[History Index]` quotes the longest request** — requests were clipped to 80 characters before the longest was picked, so every long one tied and a range quoted whichever came last (with a real model, a short follow-up instead of the 500-character request that set up the task). They are now ranked by their full length.
- **No empty `[History Index]` lines** — a compaction that summarized only the previous turn's final reply added a bare `#10–#10` line. A range with no request, file, commit or failed call now extends the range before it.
- **omp's `artifact://` store is not a file of the project** — after omp's `shake` moved tool output into `artifact://N`, the agent's read of it was listed under `[Files And Changes]` and in `mode:"touched"`. Paths with a URL scheme are left out of the file lists (the transcript still shows the read).
- **The pin notice is not repeated in the transcript** — the message `/omp-vcc-pin` sends the agent showed up as a `[user]` block in the next summary, next to `[Pinned Notes]`, which already holds the note.
- **The commands answer in print mode** — omp's print and json modes (`omp -p`) drop extension notifications, so `/omp-vcc`, `/omp-vcc-pin`, `/omp-vcc-unpin` and `/omp-vcc-recall` said nothing there, not even why nothing was compacted. They now write to stderr in those modes, as omp's own commands do; stdout stays the model's.
- **Files the session created are listed as Created** — a `write` counted as both a change and a creation, and a change always won, so `[Files And Changes]` listed every new file under `Modified` and never showed `Created`. A `write` to a path not read, edited or written before it in the window now creates it, and stays Created when it is edited later, in the same window or a later compaction; a `write` after a read or edit, or of a file the summary already lists as read or modified, is a change.
- **A clipped request says so** — a user message over 300 characters was cut at a word with no mark, so `[Early Session Requests]` and `[User Messages]` read as if the request ended there (with a real model, the cut dropped the commit message the request asked for). A clipped one now ends with `… (#N)`, the entry `vcc_recall` expands in full. `[user]` lines in the transcript carry their `(#N)` ref too; pi-vcc meant to, but dropped the index while filtering noise.
- **`vcc_recall` and `vcc_pin` lines say what they did** — the transcript showed a bare `* vcc_recall (#4)` for a `mode`, `expand`, `range` or `session` call and `* vcc_pin` for every pin, so the agent could not tell what it had already looked up. They now read like `* vcc_recall mode:sessions`, `* vcc_recall expand:[1, 25]`, `* vcc_pin "the note"`.
- **The stats toast after keeping a finished turn's reply** said `kept ~112 tok tail (mid-turn cut, no user anchor)`; it now says `kept the final reply (~112 tok)`, also when a token-budget cut lands on that reply.
- **Why nothing was compacted** — right after an automatic compaction, `/omp-vcc` said the whole session still fit in what omp always keeps, as if the session were short. It now says what came after the last compaction still fits, and "the session was just compacted" when that is the last entry. When omp-vcc's own hook cancels (too few messages), print mode gets that reason instead of a bare "Nothing to compact".
- **An empty search points at the project's earlier sessions** — when a `vcc_recall` search of the current session finds nothing and the project has earlier sessions, the result says so and names `scope:'project'` and `mode:'sessions'`. With a real model, the agent's first search of a new session came back empty, and it took another request to think of the earlier ones.
- **`[Early Session Requests]` keeps the first 3 requests** — when the first compaction kept most of the session verbatim, it saw only one or two requests, and the section never took more: the session's second and third requests (often its constraints) aged out of `[User Messages]` instead. Later compactions now fill the section up to 3.
- **A turn still running is no longer summarized away** — omp compacts between the tool calls of one turn. When that turn was the only user turn left in context and fit the 25k tail budget, the only cut was compact-all, which took the request and the tool output the agent was working from out of its context. In a test with a real model, the agent then spent request after request fetching them back with `vcc_recall`, which filled the context and compacted again. Such a pass is now left alone: a threshold or idle compaction waits until the turn has ended. An overflow or cut-off-reply recovery, which must shrink the context, keeps the turn's newest steps (at most half of it, within the tail budget) and summarizes the request and the steps before them, or summarizes the whole turn when its latest step is most of it; omp's rescue shakes what is kept and still too big. It used to step aside, and omp ran the method it had picked: on a vision model, snapcompact. `/omp-vcc`, `/compact` and explicit `keep:N` are unchanged.
- **A finished turn keeps its final reply** — in the same situation once the turn has ended, an automatic compaction, `/compact` or a plain `/omp-vcc` summarized the whole turn, reply included. It now keeps the final reply in context and summarizes the rest. Print mode (`omp -p`) printed nothing when this happened, since it prints the last reply still in context.

Found by comparing with [zhulinchng/omp-vcc](https://github.com/zhulinchng/omp-vcc), a separate omp port of pi-vcc:

- **No compaction that makes the context bigger** — when the messages to summarize were shorter than the summary that would replace them (right after omp's plan-mode "approve and compact", in a session barely past a low threshold, beside long pinned notes), compacting grew the context. Such a pass is now not written: an automatic one is skipped quietly, and a manual `/compact` or `/omp-vcc` says why. An overflow recovery that keeps part of the window is written all the same (what overflows is that kept part, and omp's rescue shakes its oversized tool output after it); one where even summarizing the whole window grows the context is cancelled with the reason, since the context is full of what no compaction removes. A summary may add up to 500 chars (more on a very large window, where its sections grow), or a quarter of what it replaces.
- **Every message in the kept tail counts toward its budget** — the tail budgets counted only a message's `content`, so a user's `!cmd` or python cell (command and output), a branch summary, an earlier compaction's summary and an `@file` mention counted as nothing, and a tail holding a 300 KB `!cmd` output was kept whole. They now count what they hold, in the tail budget, the smart keep-tail, the stats toast and the measured overhead.
- **One malformed entry no longer breaks recall or compaction** — a session entry with a null content part, tool-call arguments that are not an object, or content that is neither text nor parts threw out of search, so every `vcc_recall` query failed for the rest of the session, and out of the summary pipeline, so compaction failed too. Such entries are now read as far as they go; `#N` refs do not move.
- **`expand` shows the arguments a search matched** — search reads every tool-call argument, so a hit inside a `write`'s content or an `edit`'s new text came back as a ref whose `expand` showed only `write(path=…)`. The full view now lists the arguments the one-line form leaves out, clipped at 4,000 chars per message, as a paired result is; a smaller recall cap (a small window) clips both at the same share of it. A clipped `write` or `edit` points at `'#N:path:full'`, which reads its content in full.
- **The README describes the brief transcript as it works** — it said "about 120 recent lines"; the brief keeps its highest-signal lines within a token budget, not the latest ones.

## [0.10.0]

### Features

- **`vcc_recall` reads a range** — `range: [from, to]` returns entries `#from..#to` in order, 20 per page, so the agent can read what happened around a summary ref like `(#1253)` without guessing search terms or expanding each entry in full. Idea and first version by @Renno231 (#20).

- **Keyword search about 2x faster on large sessions** — each query term is compiled once instead of once per message, with identical results. A long query on a 17k-message session had hit the 3 s search limit under load.

### Internal

- `vcc_recall` and `/pi-vcc-recall` share one pipeline (`src/core/recall-request.ts`, `src/core/recall-run.ts`): one place picks the action, scope is applied once, and the command no longer copies the tool's search and paging code. - **The recall note no longer stacks up** — since 0.3.14 the closing "Use `vcc_recall` …" note was wrapped across two lines, so the next compaction did not recognise it, kept it inside the transcript and added another: one more note per compaction (a third of the summaries in the maintainer's own sessions carried 2 to 4). ## [0.6.0]

### Features

- **Recall `mode:"touched"` — file activity index** — answers the question agents actually ask after a compaction ("did I already edit this file, and what did I do?"). One call returns every file touched in the session mapped to the entries that touched it (`./src/core/config-manager.ts    #155 (quick_edit), #157 (edit)`), sorted by recency and paged. Classification is shape-based (a call counts when its arguments carry a path plus `content`/`edits`/`oldText`/`newText`), so custom edit tools are recognised without a tool-name allowlist and reads never pollute the index. Indices are the same global message indices `expand` uses. Ported from [pi-blackhole](https://github.com/k0valik/pi-blackhole).
- **Recall `#N:path` drill-down** — expands the file-scoped content of a single operation inside an entry (`#155:config-manager`, `:full`, or `:offset:limit` for long files), instead of the summarised `quick_edit(path=…)` line `expand` used to return. `#N` alone lists the file operations in that entry. The pattern is anchored, so an inline mention such as "see #42:auth.ts" is still an ordinary search. Ported from [pi-blackhole](https://github.com/k0valik/pi-blackhole).

### Changes

- **Invisible auto-continue** — the prompt sent after a compaction is now a custom message with empty content delivered as a follow-up (`triggerTurn`, `deliverAs:"followUp"`) and filtered out of the LLM payload by a `context` hook, instead of a user-role prompt that stayed in context for the rest of the session. Same gating, same timing, no per-compaction context cost. Pattern ported from [monotykamary/pi-vcc](https://github.com/monotykamary/pi-vcc) (`tom` branch).
- **Compaction toast reports tail tokens on budget cuts** — a budget cut keeps no whole user turn, so the old line read `kept 0/1 turns` and looked like everything was lost. It now leads with what is actually kept: `kept ~18.2k tok tail (mid-turn cut, no user anchor), summarized 42`. Turn-anchored cuts are unchanged.

### Fixes

- **Compaction: token-budget tail cut for autonomous sessions** — the tail was anchored exclusively to user-message boundaries, which breaks when a session has one user prompt and then runs on its own. With no boundary to keep, the hook fell back to compacting everything (`firstKeptEntryId` empty), orphan recovery rebuilt a window whose only user message was again at index 0, and every subsequent compaction repeated it: the working tail was lost every time, for the rest of the run. Measured on 755 real sessions, 21.7% hit this path. The default path now falls back to a token budget, cutting at the nearest non-`toolResult` boundary (never inside a `toolCall`/`toolResult` pair), mirroring pi core's `findCutPoint` semantics. The mirror case is handled too: a tail larger than 62.5k tokens (2.5x the 25k budget) is re-cut to roughly the budget, so a compaction that used to free almost nothing now does. Explicit `keep:N` is respected absolutely and is never re-cut. Audit on the same corpus: 43 of 43 rescuable sessions keep a tail (median 21.7k tokens) instead of none, 16 of 17 oversized tails drop from a median 73k to 20k tokens, and weighted fact recall for the rescued group rises 0.558 → 0.909. The 682 unaffected sessions are bit-identical.
- **Compaction: `custom_message` and `branch_summary` reached the summariser** — the live window only collected `type: "message"` entries, so anything an extension injected through `sendMessage` (including pi-vcc's own auto-continue) was invisible: not counted, and never passed to the summariser, so its content disappeared silently at every compaction. Both entry types are now converted to their message form in the live window, matching pi core, which treats them as user-role messages. Turn counting still counts only real user messages, so `keep:N` anchoring is unchanged.
- **Recall: `#N:path` drill-down honours `scope`** — the drill-down branch dispatched before scope resolution and read the session unfiltered, making it the one recall path that could return entries from abandoned branches without `scope:"all"`. The target entry is now checked against the active lineage by global index; `expandEntryFile` still loads unfiltered so `#N` stays aligned with the global message index. The same issue exists upstream in pi-blackhole and has been reported there.

Known trade-off: when an oversized tail is re-cut, facts that live in `toolResult` blocks cannot be expressed in the brief (ranking skips those blocks), so that group loses a median 0.049 weighted recall in exchange for freeing ~50k tokens per session. Raising the brief ceiling and block budget was tested and made no difference; a dedicated failures section is the actual fix and is planned. Known limit: a single message at or above the budget cannot be cut around (1 of 755 sessions).

## [0.5.0]

### Changes

- **`overrideDefaultCompaction` now defaults to `true`** — fresh installs let pi-vcc handle `/compact` and auto-threshold/overflow compaction, not just `/pi-vcc`. Existing config files keep their stored value; set `false` to restore pi core's LLM-based compaction for those paths.

### Fixes

- **File activity: case-insensitive tool matching** — `FILE_READ_TOOLS`/`FILE_WRITE_TOOLS`/`FILE_CREATE_TOOLS` were exact-match sets, so Pi's lowercase `read` tool never registered and `[Files And Changes]` emitted no `Read:` line at all (0 of 179 audited sessions produced one). Matching is now case-insensitive, mirroring the `/i` tool regexes in `core/rank.ts`.
- **File activity: recognise modern edit tools** — `quick_edit`, `target_edit` and `apply_patch` are ranked as edits in `src/core/rank.ts` but were missing from `FILE_WRITE_TOOLS`, so files changed through them never appeared under `Modified:`.
- **File activity: use hook-provided file ops** — `buildSections` never received `CompileInput.fileOps`, so the hook's authoritative read/modified sets were dropped before the summary was built. `extractFiles` already accepted the argument; it is now wired through.
- **Recall search: guard against regex backtracking** — a query such as `(a+)+$` made `searchEntries` spend ~0.5s per entry, freezing a 400-entry session for ~3.5 minutes. Patterns with an unbounded quantifier applied to a group that already contains one are now matched literally, and a 3s budget checked between entries stops a runaway search after one entry rather than the whole corpus (normal searches take ~10ms). Same corpus and query: 3.5 min → 0.7ms.
- **Recall search: don't lose results to mode detection** — `looksLikeRegex` treats any query containing `?`, `.`, `(`, `|` etc. as a single regex, so ordinary prose ("why did we drop the cache?") was matched verbatim and returned nothing. Measured across 584 real recall calls: the regex path returned zero results 47.5% of the time (median 1 hit) versus 1.1% for term search (median 98 hits), and 25.9% of queries were routed there. An empty regex result now falls through to term search instead of being returned as-is.
- **Recall tool: describe it as recall, not search** — the tool description led with "Search session history" and advertised regex, so the model filed it under keyword search and wrote regex-style queries (8.8% of 510 real queries contained `|`) instead of reaching for it when context was missing. Description, prompt snippet and parameter docs now say what it is for, prefer plain keywords, explain `scope` without internal jargon, and state plainly that only the current session is searchable. No behaviour change.

Audit on 790 real sessions: weighted recall 63.6% → 74.5% (median 68.2% → 79.3%), weighted fact density 6.00 → 7.08, summary size +6% (4183 → 4433 chars).

## [0.4.0]

### Features

- **Ranked compaction brief** — replace the fixed 120-line summary cap with signal-density-based block selection under a size-relative token budget (floor/ceiling/per-block clamp). On 794 real sessions: size parity with the old cap, recall +2.4pp, gh-recall +7pp, higher fact density.
- **Size-relative brief budget** — `maxBriefChars` now scales with transcript length between a floor (~1100 tok) and ceiling (~2000 tok) at ~15 tok/block, so large sessions are no longer starved of high-value long-tail blocks while small sessions stay tight.
- **Heredoc previews in brief** — multi-line bash (set -euo pipefail + real work) and interpreter heredocs (python3/node/ssh/sqlite3/...) now render a one-line body preview instead of a content-free opener. File-writer heredocs (cat/tee/dd) stay opener-only.
- **Hardened heredoc parsing** — tighten opener regex to reject shift ops (`8<<20`) and numeric heredocs; only treat as heredoc when a closing terminator exists downstream. Misparse rate ≤0.17% across ~105k bash blocks, fail-safe.
- **Trivial-bash penalty** — scaffolding-only bash blocks (set -e, cd, ls, echo) no longer compete with real edits for the brief budget. Failed commands (nonzero exit) are exempt since the failure is itself a state fact.
- **Segment-closing assistant boost** — assistant turns that close a segment (next renderable block is user or EOF) get a +14 score boost and 120+120 head/tail truncation instead of the old head-only budget.
- **Smart keep-tail** — when `smartKeepTail` is enabled (default true), pi-vcc estimates the keep:1 tail token count and, if ≤5k, grows keep to the largest N whose tail stays ≤25k. Explicit `keep:N` from the user is always respected.
- **Auto-continue after compaction** — continue the agent after a successful threshold compaction or overflow compaction, deferred until idle so it doesn't interrupt in-flight tool calls.
- **Token calibration from context usage** — calibrate chars/token from the real `tokensBefore` reported by the harness instead of a hardcoded heuristic, so estimates adapt to each session's content mix.

### Fixes

- **Token estimate: count all token-bearing parts** — `estimateMessageContentChars` now counts `thinking`, `toolCall.arguments` (not just `.input`), and `image` (4800 chars). Previously these were missed, deflating calibrated chars/token (mean 2.35→2.50) and over-estimating tail tokens. Fixes smart-keep engagement and brief budget sizing.
- **Brief budget: charge preserve-recent blocks** — the newest `preserveRecentBlocks` are now charged against `maxBriefChars` instead of being added unconditionally. On the largest real session (~27.9k blocks) the ranked brief was 31% larger than baseline with zero recall gain; `maxBriefChars` is now a true ceiling.
- **Notify format tightened** — compaction notify now shows `kept N/M turns, ~Xk tok (summarized Y)` instead of verbose source-entry counts and mechanism wording. Anomalies (compact-all fallback) collapse to `kept 0/N` with no extra clause.
- **Notify retained with follow-up** — compact metrics notify is no longer swallowed when a pi-vcc follow-up prompt is queued.
- **Brief: preserve message line breaks** — assistant text line breaks are no longer collapsed in the brief render.
- **Exclude tool_result from selection** — `tool_result` blocks no longer consume brief selection budget since they render to nothing.
- **gh pr poll penalty/dedup** — `gh pr view/checks <num>` polling commands get -10 penalty and are deduplicated by PR number; `gh pr merge/create/comment` are not penalized.
- **Continuation timing** — threshold continuation deferred until idle; overflow compaction continuation fixed.
- **Misc** — greptile review nits addressed; smart-keep tests aligned with compact-all boundary.
